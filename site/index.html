                                                Par écosystème

                                                Périmètre
                                                Tous les dépôts de l’organisation, PR créées au cours des 36 derniers mois. La période choisie, ou les dates choisies dans ces 36 mois, filtre les PR créées et la date des reviews, commentaires et merges. Les PR et reviews des bots sont exclues. Les deux années avant la dernière se rechargent d’un mois à chaque synchro : tant qu’elles ne sont pas toutes là, les périodes de 24 et 36 mois attendent.
                                                Comparaison
                                                Sur la vue d’ensemble, le cycle de vie, la TMA et DevOps, les chiffres de la période peuvent se comparer à la période d’avant (la même durée, juste avant) ou à la même période l’an dernier (les mêmes jours, un an plus tôt ; pour 12 mois, les deux reviennent au même : seule la période d’avant est proposée ; au-delà d’un an, l’an dernier reprendrait une partie de la période et n’est pas proposé). Les jours comparés s’affichent sous le choix. Chaque chiffre affiche alors son évolution, comme dans le bilan du mois : en pourcentage, ou en points pour les parts, en vert quand elle va dans le bon sens, en orange sinon, les volumes restant neutres. Une comparaison que les 36 mois synchronisés ne couvrent pas n’est pas proposée, et choisir une période qu’elle ne couvre plus (36 mois, par exemple) revient sans comparaison ; les exécutions de CI que GitHub a effacées n’ont pas d’évolution (« – »).
                                                PR de code
                                                Toutes les PR sauf celles de release (release/*, release-please, develop vers master) et de synchronisation de branches (merge*, back-merges, project/…/main vers develop ou master, branches de projet qui en ramènent une autre, comme project/…/merge-develop, project/…/develop-into-main ou project/…/sync-develop), comptées à part dans « Release / intég. ». Merges, délais, tailles, lignes et reviews ne portent que sur les PR de code.
                                                PR relue
                                                Au moins une review ou un commentaire de quelqu’un d’autre que l’auteur. Dans l’évolution, elle compte dans la période de la première intervention.
                                                Délais et tailles
                                                Médianes, moins sensibles que la moyenne aux quelques très grosses PR. Les délais ne comptent que les heures ouvrées, du lundi au vendredi de 9 h à 18 h, heure de Paris : une PR ouverte le vendredi soir et relue le lundi matin n’a pas attendu le week-end. Un jour compte 9 h ouvrées (« j ») ; les jours fériés comptent comme ouvrés. Seules les durées des exécutions de CI restent en temps réel. Taille : lignes ajoutées plus supprimées.
                                                Lignes ajoutées et supprimées
                                                Total des lignes des PR de code ouvertes sur la période et mergées, comptées comme GitHub : une ligne modifiée compte une fois supprimée et une fois ajoutée. Les PR de release et de synchronisation de branches n’y comptent pas, pour ne pas compter deux fois les mêmes lignes, ni celles des bots. Tous les fichiers comptent, fichiers générés et verrous de dépendances (package-lock.json, composer.lock…) compris : un gros chiffre peut en venir. Ils sont arrondis (12 k, 1,2 M), sauf dans le Bilan du mois.
                                                Type de dépôt
                                                Déduit des langages détectés par GitHub : Vue donne front ; PHP, Go, Rust donnent back ; Dart (Flutter) donne mobile ; la documentation, l’infrastructure et l’outillage sont classés « autres ». TypeScript et JavaScript comptent en front à côté de Vue, en back sinon. Quelques dépôts sont classés à la main.
                                                Stack
                                                Répartition des PR de code (auteurs) ou des PR relues (relecteurs) entre dépôts front, back et mobile, et technologies principales de ces dépôts. Les dépôts « autres » n’y comptent pas. « Full-stack » : au moins 30 % des PR côté back et au moins 30 % côté client (front ou mobile).
                                                Technologies
                                                Les langages d’un dépôt sont regroupés sous le framework que déclarent ses fichiers de dépendances (composer.json, package.json, pubspec.yaml) : PHP et Blade sous Laravel, Vue et TypeScript sous Nuxt, Dart sous Flutter, TypeScript sous NestJS… Chaque PR de code est répartie entre les technologies de son dépôt, au prorata de leur part dans le code (moins de 2 % : ignorée), tout comme, au choix, les lignes ajoutées par les PR de code mergées. Logos : Simple Icons.
                                                Cycle de vie
                                                Le temps d’une PR de code, de son ouverture à la prod, découpé en quatre étapes : la prise en charge, jusqu’à la première review ou au premier commentaire d’une autre personne ; la relecture, jusqu’à la dernière approbation avant le merge, ou jusqu’au merge sans approbation ; le merge, de cette approbation au merge ; la mise en prod, du merge à l’arrivée en prod, comme pour les indicateurs DORA. Chaque PR ouverte sur la période ne compte que dans les étapes qu’elle a franchies, et ce qui suit son merge n’y compte pas. Chaque étape a sa médiane : elles ne s’additionnent pas.
                                                Frise d’une PR
                                                Un clic sur une PR, dans n’importe quelle liste, ouvre sa frise ; Ctrl ou ⌘ + clic l’ouvre sur GitHub. En tête, son titre et l’état de la CI de son dernier commit : réussie, en échec, en erreur, en cours, attendue, ou sans CI. Seules les PR que les listes montrent ont un titre et l’état de leur CI dans les données : celles qui sont ouvertes ou ont bougé dans les 30 derniers jours, pour garder les données légères. La synchro relit à chaque passage la CI des PR ouvertes, une CI qui se termine ne modifiant pas la PR. Ses étapes : l’ouverture, la première review ou le premier commentaire d’une autre personne, chaque demande de changements et chaque approbation avant le merge, le merge, puis l’arrivée en prod d’une PR de code. Avant chaque étape, l’attente en heures ouvrées, à la minute près : la page Cycle de vie arrondit ses médianes au dixième d’heure. Une PR ouverte, en brouillon ou pas encore en prod dit depuis combien de temps elle attend, à la dernière synchro. Une PR fermée sans merge le dit, sans date : les données ne la gardent pas. Les interventions après le merge ne sont pas des étapes, mais comptent dans la liste de qui est intervenu.
                                                Bilan du mois
                                                Un mois compte, comme une période choisie, les PR ouvertes ce mois-là et les reviews, merges, déploiements et exécutions de CI de ce mois-là. Il se compare au mois précédent (en pourcentage, ou en points pour les parts) et à la médiane des 12 derniers mois complets. Une évolution est en vert quand elle va dans le bon sens (délais, hotfix, reprises, PR sans review, échecs de CI en baisse), en orange sinon ; les volumes restent neutres. La page s’ouvre sur le mois en cours : incomplet, il ne se compare pas.
                                                Tendances
                                                Les chiffres du bilan, mois par mois, sur les mois que la période touche : chacun compte en entier, même si la période n’en couvre que quelques jours, et le mois en cours, incomplet, est plus clair. Le premier mois des données, coupé par leur début, reste de côté. Sur 30 ou 90 jours, une courbe n’a que deux à quatre mois. La médiane sur 3 mois d’un mois est celle de ce mois et des deux précédents, même avant la période ; elle attend trois mois complets d’affilée et laisse de côté le mois en cours. Le dernier mois complet de la période se compare au même mois un an plus tôt et à la médiane des 12 mois complets jusqu’à lui, même s’ils sont avant la période. L’intégration continue ne remonte qu’aux exécutions que GitHub avait encore, environ 13 mois, quand le dashboard a commencé à les garder lui-même : sa carte le rappelle quand la période commence avant, et son historique s’allonge d’un mois chaque mois.
                                                Analyse
                                                Dix règles fixes croisent les chiffres de la période ; chacune ne parle que sur au moins 20 PR (10 pour un dépôt, 30 exécutions pour un workflow), et dit sinon qu’elle manque de données. Les délais sont ceux des PR relues, en heures ouvrées. Taille : les PR de 500 lignes ou plus mettent au moins deux fois plus de temps à être mergées que celles de moins de 100 lignes. PR géantes : les PR de 1 000 lignes ou plus sont mergées sans review ni commentaire au moins deux fois plus souvent que les autres, et au moins une fois sur dix. Étape avant le merge : la prise en charge, la relecture ou le merge prend en moyenne la moitié ou plus du temps des PR relues jusqu’à leur merge, quand celles-ci mettent une demi-journée ouvrée ou plus à être mergées. La mise en prod, qui suit le calendrier de déploiement de chaque dépôt, n’y compte pas. Relecteur : une seule personne de l’équipe intervient sur 60 % ou plus des PR relues d’un dépôt. Dépôts sans review : la moitié ou plus des PR mergées d’un dépôt l’ont été sans review. Workflows : un sur cinq ou plus de leurs exécutions échoue, ou leur durée médiane atteint 10 minutes. Abandon : 10 % ou plus des PR de code fermées sans merge. Tendance : la seconde moitié de la période face à la première, sa dernière semaine à part (ses PR ne sont pas toutes relues ou mergées), sur au moins 50 PR mergées par moitié ; une médiane bouge quand elle varie de moitié, une part de 5 points et d’un tiers. Un constat est prioritaire quand il dépasse nettement son seuil.
                                                Mises en production
                                                PR de release mergées dans master ou main, y compris celles de release-please.
                                                Hotfix
                                                PR de code dont la branche commence par hotfix. Part de hotfix : rapportées à toutes les PR de code.
                                                Mergées par leur auteur sans approbation
                                                PR de code des dépôts front, back et mobile que leur auteur a mergées lui-même au cours des 30 derniers jours, quelle que soit la période choisie, sans approbation d’une autre personne avant le merge. Chacune dit ce qu’elle avait reçu à la place : aucune review, des commentaires ou une demande de changements.
                                                Déploiement
                                                PR mergée dans master ou main : release, hotfix ou merge direct, hors back-merges entre ces deux branches. Les déploiements GitHub ne sont pas utilisés.
                                                Indicateurs DORA
                                                Une PR mergée dans develop arrive en prod avec le déploiement suivant de son dépôt ; mergée dans une branche de projet, une fois cette branche mergée à son tour. Les correctifs sont les déploiements imprévus pour réparer la prod : hotfix et reverts. Leur part est le taux de reprise, ajouté par DORA en 2024 ; il remplace ici le taux d’échec des déploiements, que des hotfix fréquents rendent difficile à isoler. Le rétablissement est le délai des correctifs jusqu’à leur merge en prod.
                                                Intégration continue
                                                Exécutions GitHub Actions déclenchées par une PR ou un push, hors exécutions planifiées, manuelles et de Dependabot. Seules celles qui aboutissent à un verdict comptent : annulées et ignorées sont exclues. Elles sont regroupées par jour, et une période compte ses jours en entier. GitHub efface les exécutions au bout d’environ 13 mois : la CI ne remonte qu’aux exécutions que la synchro a déjà lues, et s’allonge avec le temps jusqu’à 36 mois. Une période qui commence avant compte la CI depuis sa première exécution gardée, et le bilan d’un mois plus ancien n’en a pas. Check rouge : au moins un check en échec sur le dernier commit de la PR, checks facultatifs compris (Sentry, CodeRabbit…).
                                                Dependabot
                                                PR de mise à jour de dépendances ouvertes par Dependabot, comptées à part des PR de code. Celles mergées dans master ou main comptent aussi comme déploiements.
                                                Binôme
                                                Un auteur et une personne qui intervient sur ses PR de code. Chaque PR ouverte sur la période compte une fois pour chaque relecteur distinct, quel que soit le nombre de reviews ou de commentaires, et quelle que soit la date de ces interventions. L’auteur ne compte jamais comme son propre relecteur.
                                                Dépendance au relecteur principal
                                                Part des PR relues d’un auteur sur lesquelles intervient son relecteur le plus fréquent. Proche de 100 % avec plusieurs PR, elle signale un binôme figé : le code de l’auteur n’est connu que d’une autre personne. Ces indicateurs servent à repérer des risques d’équipe, pas à classer des personnes.
                                                Bus factor
                                                Le plus petit nombre de personnes de l’équipe qui ont écrit à elles seules au moins la moitié des PR de code d’un dépôt sur la période. À 1, le dépôt repose sur une seule personne ; « Auteurs partis » : les personnes encore là en ont écrit moins de la moitié. Il ne dit rien de la qualité du code, seulement du risque de le voir n’être connu de personne.
                                                À débloquer
                                                PR de code ouvertes, hors brouillons et PR des personnes parties, classées comme GitHub selon la dernière décision de chaque relecteur : des changements demandés par quelqu’un, sinon des code owners qui ne l’ont pas encore relue alors que GitHub ne la laisse pas merger, sinon autant d’approbations qu’il en faut pour merger, sinon moins, sinon des reviews ou commentaires sans décision, sinon rien. Une PR n’y apparaît qu’après un jour ouvré approuvée, bloquée par un code owner ou sans review, trois jours ouvrés avec des changements demandés ou en discussion, comptés depuis cette décision, l’ouverture ou le dernier échange. Sans aucune review ni commentaire depuis plus d’un mois, elle est rangée à part, parmi les oubliées.
                                                Pour moi
                                                Les mêmes PR ouvertes, vues par la personne choisie, celles de release et d’intégration comprises (étiquetées : À débloquer ne garde que le code) : celles des autres dont GitHub lui demande encore la review (une demande faite à une équipe ne compte pas, la synchro ne sait pas qui en fait partie ; elle s’efface dès que la personne a relu la PR), puis les siennes, chacune dans une seule liste, définie comme sur À débloquer mais sans délai minimum. Oubliée d’abord, sans aucune review ni commentaire depuis plus d’un mois, quoi qu’elle attende ; sinon prête à merger, approuvée par autant de personnes qu’il en faut, avec des changements demandés, bloquée par un code owner, ou, pour toutes les autres, dans ses PR ouvertes.
                                                Noms
                                                Nom du profil GitHub, sinon identifiant.
                                                Anciens collaborateurs
                                                Une personne sans aucune PR, review, commentaire ni merge depuis un mois est considérée comme partie : plus de ligne, de carte ni de place dans les listes et la matrice à son nom, seulement une mention dans la partie « Anciens collaborateurs » de la page Équipe et parmi les champions de chaque mois du Palmarès. Ses PR restent comptées dans les totaux, les graphiques et les dépôts. Dans les dépôts portés par une seule personne, celle qui en a écrit le plus reste nommée même partie, marquée « hors équipe » : son code est toujours là. Le bus factor ne compte que l’équipe actuelle.

                                                Données GitHub actualisées automatiquement : tant qu’elle est affichée, ou en arrière-plan avec les notifications de « Pour moi », la page lance une synchro rapide dès qu’elles ont plus de 10 minutes, et le workflow tourne aussi en semaine, à intervalles irréguliers. Pour les mettre à jour tout de suite, utilise le bouton ⟳ de la navigation, ou ouvre le workflow Sync and deploy puis clique sur « Run workflow » (accès en écriture au dépôt requis).

                                                Lancer une synchro complète ?

                                                Elle relit depuis GitHub toutes les PR des 12 derniers mois, dépôt par dépôt, avec leurs checks : 15 à 20 minutes. Les PR plus anciennes restent telles qu’elles ont été lues. Pendant ce temps, les autres synchros attendent leur tour et la page garde les données actuelles.

                                                Elle doit rester exceptionnelle : seulement si des données semblent fausses ou manquantes. Pour les dernières PR, la synchro rapide suffit.
